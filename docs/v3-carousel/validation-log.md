# V3 智能分页验证记录

本文件按 `next-development.md` §3A 的要求，记录智能分页在固定种子下的可复现验证结果。
所有结论都能用本文件给出的参数重跑；没有只凭一套演示图得出的判断。

**验证方式：** 不依赖浏览器的算法级验证（纯函数直接跑固定种子矩阵），配合 `npm test` 中的
`src/v3-carousel/layout/carouselSmartPagination.test.js` 与 `carouselPlacement.test.js`。
**本次未做：** 浏览器截图与肉眼观感确认（见第 6 节待办）。

## 1. 结论摘要

| 不变量 | 结果 |
| --- | --- |
| 照片数量守恒、不丢图、不重复 | 通过（1–24 张 × 全部样本 × 全部种子） |
| 每页 2 / 3 / 4 张，4 张页最多一次 | 分页计划通过；**实际输出在超宽 / 超长照片上会出现单图页**（见 3.1） |
| 2 张页多于 3 张页 | 通过（5 张照片是算术上唯一不可满足的例外：只能拆成 2+3） |

| 10–13 张优先五页；照片多时宁可加页 | 通过（24 张 → 10 页，未被强行封顶在 8 页） |

| 固定 seed 可复现 | 通过（分页与几何都完全一致） |
| 不拉伸照片 | 通过（内容区反推比例与原始比例最大偏差 0.56%，来源见 4.3） |

| 白边 2–5px | 落在区间内，但合法尺寸下实测只会取到 3–5px（见 4.2） |
| 每页 2–4 张（含超宽 / 超长） | 通过：自动缩放上线后单图页归零（见 3.1、7） |

## 3. 已复现的异常与规则冲突

### 3.1 超宽 / 超长照片会独占一页（单图页）——已修复

**状态：** 已由「整页自动缩放」修复（决策与实现见第 7 节）。保留本节作为问题记录与回归依据。

**现象：** 实际输出页数多于分页计划，多出来的页只放 1 张照片，且照片必然是超宽或超长图。

**复现（默认 demo 数据，无需上传）：**

```text
/?prototype=carousel-smart&variant=gallery&demo=10   seed 改成 6
  分页计划: 2 · 2 · 2 · 2 · 2   (5 页)
  实际输出: 2 · 1 · 1 · 2 · 2 · 2   (6 页)
  第 2 页只有 demo-3.jpg (2.5:1)
  第 3 页只有 demo-5.jpg (1:2.5)
  内容区碰撞 0

对照 seed 4128（默认值）：2 · 2 · 2 · 2 · 2，5 页，其中 demo-3 与 demo-5 正常同页。
```

**频率（demo 数据，count 4–24 × 三种风格 × seed 1–120，共 7560 个计划）：**

- 输出页数多于分页计划：668 个计划，8.8%。
- 单图页总数 1336，构成：超宽（>1.8）668 + 超长（<0.56）668，**普通比例 0**。
- count=6 / count=10 的 gallery，400 个种子里 67 个（16.8%）出现单图页。
- 常规比例样本（0.75–1.33）在 1–24 张、三种风格、多个种子下：单图页 0。

**根因（代码级）：** `carouselSmartPagination.js` 的横竖配对会给「横 + 竖」最高优先级，
而超宽（2.5:1）与超长（1:2.5）正好被判为最理想的一对；但几何上这两张恰好是最不可能共存的一对：
超宽图被 80% 宽度上限撑满整页宽度，超长图接近 78% 高度上限，两者在 96%×88% 的安全区里没有合法位置，
于是一起顺延，各自独占一页。配对规则与尺寸边界互相打架，不是随机失败。

**性质判断与最终处理：** 这一现象曾被解释为设计意图（`direction.md` §5.1「出现超宽图 → 独立成为横向安静段落」），
但它与 `development-guardrails.md` §3「正常页只能有 2、3 或 4 张照片」冲突，界面也会同时显示
「智能分页：2 · 2 · 2 · 2 · 2 张 / 页」和「6 页输出」，自相矛盾。

**产品决定（已确认并实现）：** 改成「整页自动缩放」——一页放不下时把该页所有卡片统一下调尺寸重排，
而不是让一张照片顺延成单图页。规则与实测见第 7 节。

### 3.2 「短边 ≥ 20%」与「宽 ≤ 80% / 高 ≤ 78%」在极端比例下互斥

单张照片独占一页时可达到的最大内容短边（占页宽比例）：

| 照片比例 | 内容短边 | 是否满足 20% |
| --- | --- | --- |
| 3.8 : 1 | 0.209 | 是 |
| 4 : 1 | 0.200 | 临界（数学分界点） |
| 4.2 : 1 | 0.191 | 否 |
| 5 : 1 | 0.160 | 否 |
| 1 : 0.22 | 0.213 | 是 |
| 1 : 0.205 | 0.200 | 临界 |
| 1 : 0.20 | 0.195 | 否 |

**结论：** 只有当比例落在 **1:4 – 4:1** 之间时，20% 最小短边与 80%/78% 最大内容才可能同时满足；
更极端时必须放弃其中一条。默认 demo 数据的比例范围是 0.4–2.67，因此演示模式碰不到这个冲突，
**只有真实上传的全景图（例如 5:1）才会触发**。

**产品决定（已确认）：** 20% 从硬下限改为**优先下限**（`development-guardrails.md` §3）：
极端比例允许短边低于 20%（保完整展示，与 `direction.md` §5.2「比例极端：默认完整展示」一致），
这类照片的可读性判据改用「长边不低于页面短边的 20%」。

## 4. 观察项（不是错误，但影响判断）

### 4.1 分页计划与实际输出页数可能不一致

界面的「智能分页：… 张 / 页」显示的是计划，而「N 页输出」显示的是实际帧数。
自动缩放上线后，demo 与极端比例样本集的「输出多于计划」都归零（第 7 节）；
只有在自动缩放试到底仍放不下、需要补充页时才会重新出现差异。

### 4.2 白边 2px 在合法尺寸下取不到

`matFor()` 声明范围 2–5px，实测在满足 20% 短边下限的照片上只会取到 3–5px；
2px 需要内容短边低于约 15.4%，也就是只有比 5.2:1 更极端的照片才会出现。
文档里的「2–5px」应理解为「3–5px 为主，极端情况可到 2px」。

### 4.3 内容区反推比例有 0.56% 的最大偏差

`sizeFor()` 用**内容尺寸**算白边，`innerBox()` 用**外卡片尺寸**再算一次白边，
两次 `matFor()` 可能差 1px，导致 `innerBox()` 只是内容区的近似值（实测最大相对偏差 0.56%）。
碰撞判定内部是自洽的（`contentCollisions` 始终为 0），但这个 1px 差异意味着
**CSS 真正渲染的 padding 与碰撞计算用的白边不是同一个值**。

另有尺度问题：`--scatter-mat` 是裸 px，而 `innerBox()` 按 1080×1350 单页导出尺度计算。
屏幕上每页只有约 178–216px 宽（1080 被 N 页平分），所以预览里的白边比真实导出视觉上粗约 5 倍。
**在补导出功能前，预览不能当作「单独导出每页」的可信代理。**

### 4.4 10 张照片时页数方案唯一

10 张只有 `2 · 2 · 2 · 2 · 2` 一种分解，所以「换一组排法」在 10 张时只改变每页内部构图，
不会改变页数结构。这是正常行为，已写成测试固定下来。

## 7. 自动缩放：候选方案验证与落地

产品负责人提出的方向：**超长图限制死、缩放到一页摆得下；超宽图限制在一页内。**
先按原型验证两个规则（一次性代码，`npm run prototype:v3-fit`），再决定落地哪一条。

| 规则 | 做法 |
| --- | --- |
| 规则 1 缩到一页摆得下 | 一页放不下时，整页所有卡片统一下调尺寸重排，从 100% 起每次 -7% 试到 48%，取「整页都放得下」的最大缩放 |
| 规则 2 超宽上限 | 超宽图（>1.8）内容宽度上限从 80% 收到 62% |

**原型结果（1–24 张 × 三种风格 × 40 个种子，逐样本集统计单图页）：**

| 规则组合 | demo | 只有超长 | 只有超宽 | 超长为主 | 只有常规 | 最差短边 | 输出多于计划 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 现状（都不开） | 616 | 595 | 0 | 220 | 0 | 16.0% | 1123 |
| **只开规则 1** | **0** | **0** | **0** | **0** | **0** | **15.6%** | **0** |
| 只开规则 2 | 0 | 595 | 0 | 220 | 0 | 12.4% | 815 |
| 规则 1+2 | 0 | 0 | 0 | 0 | 0 | 12.4% | 0 |

**结论与落地：**

1. **只落地规则 1**。它在所有样本集上把单图页与「输出多于计划」同时清零，包括规则 2 完全无效的
   「只有超长」照片集（竖图并排放不下才是更基础的冲突）。
2. **规则 2 不做**：在规则 1 之上零收益，只会把超宽图短边从 16.0% 压到 12.4%。
   因此「超宽图横跨两页」也不必做 —— 它还会与 `direction.md` §5.3「主体不跨切线」
   和 §8.4「单独导出的每页仍然完整」冲突。
3. **代价**：拥挤页的短边会低于 20%（极端竖图集最差 15.6%；8:1 全景按自身比例是 8.0%）。
   产品已确认 20% 从硬下限改为**优先下限**，见 `development-guardrails.md` §3；
   这类照片的可读性判据改用长边（实测极端样本集最差 41.6%）。
   实测中曾试过再加一条 14% 的短边硬下限，但它会让「超宽 + 超长」重新退回单图页，
   与「限制死、缩到一页摆得下」的意图相反，因此去掉；阶梯下限 48% 就是缩放的实际边界。
4. **改动范围可控**：自动缩放只在整页放不下时触发。按照片集合配对比较 54213 页，
   现状下已经成功的页**几何完全一致、一页未改**；相同 seed 结果仍然确定。

**落地后的实测（`carouselPlacement.js`，count 4–24 × 3 风格 × 11 种子，每个样本集）：**

| 样本集 | 单图页 | 输出多于计划 | 丢图 | 碰撞 | 最小短边 | 最小长边 | 用到的缩放档 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| demo | 0 | 0 | 0 | 0 | 20.0% | 20.0% | 100 / 93 |
| 常规比例 | 0 | 0 | 0 | 0 | 20.0% | 20.0% | 100 |
| 只有超长 | 0 | 0 | 0 | 0 | 15.6% | 41.6% | … 80 |
| 只有超宽 | 0 | 0 | 0 | 0 | 16.0% | 49.4% | 100 |
| 超宽超长混合 | 0 | 0 | 0 | 0 | 13.8% | 43.0% | … 86 |
| 极端（8:1 / 1:8） | 0 | 0 | 0 | 0 | 8.0% | 64.0% | … 80 |

（8:1 全景的 8.0% 是它自己的比例决定的：长边 64% 时短边必然是 8%。）

## 8. 手机预览：改成一页一屏（界面改动，非算法）

浏览器实测（Chrome CDP，390×844 手机视口 / 1440×900 桌面视口，`demo=10`）：

| | 改前 | 改后 |
| --- | --- | --- |
| 单页尺寸（手机） | 220 × 275 | **335 × 419**（仍是 4:5） |
| 主图实际像素 | 138 × 106 | **210 × 160** |
| 细节图实际像素 | 59 × 76 | **92 × 121** |
| 手机上能同时完整看到几页 | 1 | 1（但页宽占满屏幕，左右各露 7vw 相邻页） |
| 横滑是否按页吸附 | 否 | 是（实测 `scrollLeft` 落在 308 / 643，正好是页距 − 7vw） |
| 桌面（1440） | 1080 宽的整条带子，5 页各 216 × 270 | 不变 |

**改动只在一个媒体查询里**（`CarouselScatterPrototype.css` 的 `max-width: 620px`）：每页列宽
220px → 86vw，页高按 4:5 推出，`.carousel-master__stage` 加 `scroll-snap-type: x mandatory`
与 `scroll-padding-left: 7vw`，`.scatter-frame` 加 `scroll-snap-align: start`。

**踩到的一个坑（记录以免再犯）：** 只加 `scroll-snap-type` 时吸附不生效 —— 母板给
`.carousel-master__strip` 设了 `overflow: hidden`，这让带子自己成为滚动容器，于是每页的吸附点被绑到
带子（而带子没有 `snap-type`）上。移动端把带子改成 `overflow: visible` 后吸附才生效；
每页的卡片仍由 `.carousel-master__frame` 自己的 `overflow: hidden` 裁切，Weekend 的旋转卡片实测不会串页。

**仍未解决：** 一页 2–4 张时，细节图在手机上仍只有 ~90px；这是「4:5 页面 + 多张照片」的构图取舍，
要么接受，要么以后做「点按放大单张」，靠改预览尺寸解决不了。
