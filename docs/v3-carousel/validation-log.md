# V3 智能分页验证记录

本文件按 `next-development.md` §3A 的要求，记录智能分页在固定种子下的可复现验证结果。
所有结论都能用本文件给出的参数重跑；没有只凭一套演示图得出的判断。

**验证方式：** 不依赖浏览器的算法级验证（纯函数直接跑固定种子矩阵），配合 `npm test` 中的
`src/v3-carousel/layout/carouselSmartPagination.test.js` 与 `carouselPlacement.test.js`。
**本次未做：** 浏览器截图与肉眼观感确认（见第 6 节待办）。

## 1. 结论摘要

| 不变量 | 结果 |
| --- | --- |
| 照片数量守恒、不丢图、不重复 | 通过（1–24 张 × 全部样本 × 全部种子） |
| 每页 2 / 3 / 4 张，4 张页最多一次 | 分页计划通过；**实际输出在超宽 / 超长照片上会出现单图页**（见 3.1） |
| 2 张页多于 3 张页 | 通过（5 张照片是算术上唯一不可满足的例外：只能拆成 2+3） |
| 4 张页不落在开头 / 结尾 | 通过（21 档 × 500 个种子） |
| 10–13 张优先五页；照片多时宁可加页 | 通过（24 张 → 10 页，未被强行封顶在 8 页） |
| 三种风格共用同一套分页计划 | 通过（同 seed 下 gallery / muse / weekend 的 `pagePlan` 完全一致） |
| 固定 seed 可复现 | 通过（分页与几何都完全一致） |
| 不拉伸照片 | 通过（内容区反推比例与原始比例最大偏差 0.56%，来源见 4.3） |
| 照片内容区不碰撞 | 通过（全部样本 `contentCollisions = 0`） |

| 白边 2–5px | 落在区间内，但合法尺寸下实测只会取到 3–5px（见 4.2） |
| 每页 2–4 张（含超宽 / 超长） | 通过：自动缩放上线后单图页归零（见 3.1、7） |

## 3. 已复现的异常与规则冲突

### 3.1 超宽 / 超长照片会独占一页（单图页）——已修复

**状态：** 已由「整页自动缩放」修复（决策与实现见第 7 节）。保留本节作为问题记录与回归依据。

**现象：** 实际输出页数多于分页计划，多出来的页只放 1 张照片，且照片必然是超宽或超长图。

**复现（默认 demo 数据，无需上传）：**

```text
/?prototype=carousel-smart&variant=gallery&demo=10   seed 改成 6
  分页计划: 2 · 2 · 2 · 2 · 2   (5 页)
  实际输出: 2 · 1 · 1 · 2 · 2 · 2   (6 页)
  第 2 页只有 demo-3.jpg (2.5:1)
  第 3 页只有 demo-5.jpg (1:2.5)
  内容区碰撞 0

对照 seed 4128（默认值）：2 · 2 · 2 · 2 · 2，5 页，其中 demo-3 与 demo-5 正常同页。
```

**频率（demo 数据，count 4–24 × 三种风格 × seed 1–120，共 7560 个计划）：**

- 输出页数多于分页计划：668 个计划，8.8%。
- 单图页总数 1336，构成：超宽（>1.8）668 + 超长（<0.56）668，**普通比例 0**。
- count=6 / count=10 的 gallery，400 个种子里 67 个（16.8%）出现单图页。
- 常规比例样本（0.75–1.33）在 1–24 张、三种风格、多个种子下：单图页 0。

**根因（代码级）：** `carouselSmartPagination.js` 的横竖配对会给「横 + 竖」最高优先级，
而超宽（2.5:1）与超长（1:2.5）正好被判为最理想的一对；但几何上这两张恰好是最不可能共存的一对：
超宽图被 80% 宽度上限撑满整页宽度，超长图接近 78% 高度上限，两者在 96%×88% 的安全区里没有合法位置，
于是一起顺延，各自独占一页。配对规则与尺寸边界互相打架，不是随机失败。

**性质判断与最终处理：** 这一现象曾被解释为设计意图（`direction.md` §5.1「出现超宽图 → 独立成为横向安静段落」），
但它与 `development-guardrails.md` §3「正常页只能有 2、3 或 4 张照片」冲突，界面也会同时显示
「智能分页：2 · 2 · 2 · 2 · 2 张 / 页」和「6 页输出」，自相矛盾。

**产品决定（已确认并实现）：** 改成「整页自动缩放」——一页放不下时把该页所有卡片统一下调尺寸重排，
而不是让一张照片顺延成单图页。规则与实测见第 7 节。

### 3.2 「短边 ≥ 20%」与「宽 ≤ 80% / 高 ≤ 78%」在极端比例下互斥

单张照片独占一页时可达到的最大内容短边（占页宽比例）：

| 照片比例 | 内容短边 | 是否满足 20% |
| --- | --- | --- |
| 3.8 : 1 | 0.209 | 是 |
| 4 : 1 | 0.200 | 临界（数学分界点） |
| 4.2 : 1 | 0.191 | 否 |
| 5 : 1 | 0.160 | 否 |
| 1 : 0.22 | 0.213 | 是 |
| 1 : 0.205 | 0.200 | 临界 |
| 1 : 0.20 | 0.195 | 否 |

**结论：** 只有当比例落在 **1:4 – 4:1** 之间时，20% 最小短边与 80%/78% 最大内容才可能同时满足；
更极端时必须放弃其中一条。默认 demo 数据的比例范围是 0.4–2.67，因此演示模式碰不到这个冲突，
**只有真实上传的全景图（例如 5:1）才会触发**。

**产品决定（已确认）：** 20% 从硬下限改为**优先下限**（`development-guardrails.md` §3）：
极端比例允许短边低于 20%（保完整展示，与 `direction.md` §5.2「比例极端：默认完整展示」一致），
这类照片的可读性判据改用「长边不低于页面短边的 20%」。

## 4. 观察项（不是错误，但影响判断）

### 4.1 分页计划与实际输出页数可能不一致

界面的「智能分页：… 张 / 页」显示的是计划，而「N 页输出」显示的是实际帧数。
自动缩放上线后，demo 与极端比例样本集的「输出多于计划」都归零（第 7 节）；
只有在自动缩放试到底仍放不下、需要补充页时才会重新出现差异。

### 4.2 白边 2px 在合法尺寸下取不到

`matFor()` 声明范围 2–5px，实测在满足 20% 短边下限的照片上只会取到 3–5px；
2px 需要内容短边低于约 15.4%，也就是只有比 5.2:1 更极端的照片才会出现。
文档里的「2–5px」应理解为「3–5px 为主，极端情况可到 2px」。

### 4.3 内容区反推比例有 0.56% 的最大偏差

`sizeFor()` 用**内容尺寸**算白边，`innerBox()` 用**外卡片尺寸**再算一次白边，
两次 `matFor()` 可能差 1px，导致 `innerBox()` 只是内容区的近似值（实测最大相对偏差 0.56%）。
碰撞判定内部是自洽的（`contentCollisions` 始终为 0），但这个 1px 差异意味着
**CSS 真正渲染的 padding 与碰撞计算用的白边不是同一个值**。

另有尺度问题：`--scatter-mat` 是裸 px，而 `innerBox()` 按 1080×1350 单页导出尺度计算。
屏幕上每页只有约 178–216px 宽（1080 被 N 页平分），所以预览里的白边比真实导出视觉上粗约 5 倍。
**在补导出功能前，预览不能当作「单独导出每页」的可信代理。**

### 4.4 10 张照片时页数方案唯一

10 张只有 `2 · 2 · 2 · 2 · 2` 一种分解，所以「换一组排法」在 10 张时只改变每页内部构图，
不会改变页数结构。这是正常行为，已写成测试固定下来。

## 7. 自动缩放：候选方案验证与落地

产品负责人提出的方向：**超长图限制死、缩放到一页摆得下；超宽图限制在一页内。**
先按原型验证两个规则（一次性代码，`npm run prototype:v3-fit`），再决定落地哪一条。

| 规则 | 做法 |
| --- | --- |
| 规则 1 缩到一页摆得下 | 一页放不下时，整页所有卡片统一下调尺寸重排，从 100% 起每次 -7% 试到 48%，取「整页都放得下」的最大缩放 |
| 规则 2 超宽上限 | 超宽图（>1.8）内容宽度上限从 80% 收到 62% |

**原型结果（1–24 张 × 三种风格 × 40 个种子，逐样本集统计单图页）：**

| 规则组合 | demo | 只有超长 | 只有超宽 | 超长为主 | 只有常规 | 最差短边 | 输出多于计划 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 现状（都不开） | 616 | 595 | 0 | 220 | 0 | 16.0% | 1123 |
| **只开规则 1** | **0** | **0** | **0** | **0** | **0** | **15.6%** | **0** |
| 只开规则 2 | 0 | 595 | 0 | 220 | 0 | 12.4% | 815 |
| 规则 1+2 | 0 | 0 | 0 | 0 | 0 | 12.4% | 0 |

**结论与落地：**

1. **只落地规则 1**。它在所有样本集上把单图页与「输出多于计划」同时清零，包括规则 2 完全无效的
   「只有超长」照片集（竖图并排放不下才是更基础的冲突）。
2. **规则 2 不做**：在规则 1 之上零收益，只会把超宽图短边从 16.0% 压到 12.4%。
   因此「超宽图横跨两页」也不必做 —— 它还会与 `direction.md` §5.3「主体不跨切线」
   和 §8.4「单独导出的每页仍然完整」冲突。
3. **代价**：拥挤页的短边会低于 20%（极端竖图集最差 15.6%；8:1 全景按自身比例是 8.0%）。
   产品已确认 20% 从硬下限改为**优先下限**，见 `development-guardrails.md` §3；
   这类照片的可读性判据改用长边（实测极端样本集最差 41.6%）。
   实测中曾试过再加一条 14% 的短边硬下限，但它会让「超宽 + 超长」重新退回单图页，
   与「限制死、缩到一页摆得下」的意图相反，因此去掉；阶梯下限 48% 就是缩放的实际边界。
4. **改动范围可控**：自动缩放只在整页放不下时触发。按照片集合配对比较 54213 页，
   现状下已经成功的页**几何完全一致、一页未改**；相同 seed 结果仍然确定。

**落地后的实测（`carouselPlacement.js`，count 4–24 × 3 风格 × 11 种子，每个样本集）：**

| 样本集 | 单图页 | 输出多于计划 | 丢图 | 碰撞 | 最小短边 | 最小长边 | 用到的缩放档 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| demo | 0 | 0 | 0 | 0 | 20.0% | 20.0% | 100 / 93 |
| 常规比例 | 0 | 0 | 0 | 0 | 20.0% | 20.0% | 100 |
| 只有超长 | 0 | 0 | 0 | 0 | 15.6% | 41.6% | … 80 |
| 只有超宽 | 0 | 0 | 0 | 0 | 16.0% | 49.4% | 100 |
| 超宽超长混合 | 0 | 0 | 0 | 0 | 13.8% | 43.0% | … 86 |
| 极端（8:1 / 1:8） | 0 | 0 | 0 | 0 | 8.0% | 64.0% | … 80 |

## 8. 手机预览：改成一页一屏（界面改动，非算法）

浏览器实测（Chrome CDP，390×844 手机视口 / 1440×900 桌面视口，`demo=10`）：

| | 改前 | 改后 |
| --- | --- | --- |
| 单页尺寸（手机） | 220 × 275 | **335 × 419**（仍是 4:5） |
| 主图实际像素 | 138 × 106 | **210 × 160** |
| 细节图实际像素 | 59 × 76 | **92 × 121** |
| 手机上能同时完整看到几页 | 1 | 1（但页宽占满屏幕，左右各露 7vw 相邻页） |
| 横滑是否按页吸附 | 否 | 是（实测 `scrollLeft` 落在 308 / 643，正好是页距 − 7vw） |
| 桌面（1440） | 1080 宽的整条带子，5 页各 216 × 270 | 不变 |

**改动只在一个媒体查询里**（`CarouselScatterPrototype.css` 的 `max-width: 620px`）：每页列宽
220px → 86vw，页高按 4:5 推出，`.carousel-master__stage` 加 `scroll-snap-type: x mandatory`
与 `scroll-padding-left: 7vw`，`.scatter-frame` 加 `scroll-snap-align: start`。

**踩到的一个坑（记录以免再犯）：** 只加 `scroll-snap-type` 时吸附不生效 —— 母板给
`.carousel-master__strip` 设了 `overflow: hidden`，这让带子自己成为滚动容器，于是每页的吸附点被绑到
带子（而带子没有 `snap-type`）上。移动端把带子改成 `overflow: visible` 后吸附才生效；
每页的卡片仍由 `.carousel-master__frame` 自己的 `overflow: hidden` 裁切，Weekend 的旋转卡片实测不会串页。

**仍未解决：** 一页 2–4 张时，细节图在手机上仍只有 ~90px；这是「4:5 页面 + 多张照片」的构图取舍，
要么接受，要么以后做「点按放大单张」，靠改预览尺寸解决不了。

## 9. 逐页导出：4:5 / 3:4 / 4:3（按页面比例分别构图）

**产品决定（已确认）：** 输出三种规格，都是逐页 PNG，文件名 `albummm-v3-<规格>-<页号>.png`：

| 规格 id | 尺寸（1080 宽） | 页面比例 | 用途 |
| --- | --- | --- | --- |
| `4x5` | 1080 × 1350 | 4:5 | 主规格；Instagram 轮播 feed / 小红书 |
| `3x4` | 1080 × 1440 | 3:4 | 更方的竖版（产品追加；与 4:5 只差 6.7% 高度，构图不同但观感接近） |
| `4x3` | 1080 × 810 | 4:3 | 横版 / 相纸比例 |

**先试过、被否掉的方案：** 第二种规格最初做成 `9x16`（1080×1920），做法是「4:5 作品垂直居中 + 上下延伸纸面」。
实测上下各留 285px 空白（占画布 30%），产品判断「相纸就是画面，不该空着」，因此先换成 4:3、随后又追加 3:4。
**教训：另一种规格不能靠缩放 / 留白塞进另一种画布，必须按该比例重新构图 —— 这正是下面参数化的原因。**

**页面规格参数化（`carouselPlacement.js` 的 `PAGE_FORMATS`）：**

- 每个规格带 `width / height / aspect`，`planSmartStory(photos, seed, style, format)` 按该比例重新排版：
  同一组照片、同一个 seed，不同规格得到**构图不同但照片集合相同**的页面（有测试断言每个规格的几何必然与 4:5 不同）。
- 分页与页面比例无关：所有规格的 `pagePlan` 完全一致（有测试断言）。
- 「内容短边 ≥ 页面短边的 20%」按比例换算：竖版页面的短边是宽（下限 0.2 页宽），横版是 0.75 页宽
  （下限 **0.15 页宽**），由 `shortEdgeFloor(format)` 统一给出。
- **加一个规格只是加一行常数**（3:4 就是这么加上去的：`{ width: 1080, height: 1440, aspect: 3 / 4 }`），
  预览切换、导出按钮、逐页背景切片、文件名全部由规格表驱动。
- **4:5 路径逐比特不变**：参数化之前导出的 5 个文件是 225 / 109 / 262 / 102 / 277 KB，
  之后每次重新导出都是同样的字节数 —— 说明改动只影响新规格。V3 测试 32 条全绿。

**连续背景怎么切页（关键实现）：** 背景挂在整条带子上（Muse 是横跨整组的渐变，Gallery/Weekend 是贯穿的
网格），所以导出单页时必须把同一张背景**平移到本页位置**：

- 网格类：`background-position-x: calc(var(--scatter-page-index) * -1080px)`，位相与连续带子完全一致，
  逐页之间不会有接缝错位（不需要让网格尺寸整除 1080）。
- Muse 渐变：`background-size: calc(var(--scatter-page-count) * 1080px) 100%`，取到的就是那一格。
- 页面装饰（muse/weekend 的第 2/3/4/5 页色块）在导出画布里没有兄弟节点，按 `data-scatter-page` 另挂一遍。

**白边尺度修正（修掉 §4.3）：** `--scatter-mat` 由裸 px 改成**按页宽百分比**（`matFor()/页宽`）。
CSS 里百分比 padding 以父级宽度为基准，换算出的水平内缩就是 `mat / 页宽`、垂直内缩是 `mat / 页高` ——
与 `innerBox()` 完全一致（`carouselPlacement.test.js` 里有一条一致性测试对两种规格逐值比对）。
实测效果：手机上单页 335px 宽时白边从 5px 变成 1.55px，与 1080 导出按比例缩放后一致，**预览即导出**。

**实测（headless Chrome 真点按钮，导出目录落盘）：**

| 检查 | 结果 |
| --- | --- |
| 三种规格导出 | 15 个文件：1080×1350（4:5）/ 1080×1440（3:4）/ 1080×810（4:3） |
| 手机视口（390×844） | 预览单页 335×419（4:5）/ 335×447（3:4）/ 335×252（4:3），导出尺寸正确 |
| 逐页内容是否不同 | SHA256 两两不同，确实逐页不同 |
| 预览与导出是否同一构图 | 同一 `format` 下卡片位置一致；4:5 导出文件大小与参数化前完全一致 |
| 页码开关 | 关掉后预览里 `.carousel-master__number` 数量 5 → 0，导出同步去掉 |

**踩到的两个坑（都已修，记下来避免再犯）：**

1. **`height: 0` 的页**：预览里每页的高度来自带子的 grid 拉伸；导出画布里它是普通块，卡片又都是绝对定位、
   不撑高度，于是页高为 0，再叠加 `overflow: hidden`，整页被裁成空白 —— 导出结果只剩纸面背景，
   而且五页字节完全相同（很隐蔽）。修法是导出时给页显式 `height: 100%`。
2. **离屏偏移不能放在被截图的节点上**：`html-to-image` 会把节点的定位一起克隆，`position: fixed; left: -20000px`
   会被原样带进 SVG 的 `foreignObject`，画面直接画到画布外。偏移要放在外层 holder 上，被截节点保持普通定位。

**已知取舍：**

- 页码现在是开关（默认开）：`direction.md` §3 把编号当作连续感手段之一，但 §6 又说 Gallery「文字几乎消失」，
  两者有张力；先做成可切换，用真实发布效果决定。
- 连续导出多张时，安卓 Chrome 会问一次「是否允许下载多个文件」。
- 导出的是预览图管线（最长边 1600px）：1080 页里照片最多占 864px 宽 / 1053px 高，全程缩小、不会放大。
- 4:3 页面更「扁」，一页 2 张时更容易触发整页自动缩放（实测同一组 demo 数据下 4:3 有 2 页缩放、最小 74%），
  这是比例带来的必然结果，不是缺陷。

## 10. 背景目前是固定的一套占位纸面

现在三种风格的背景（纸色 + 网格 / 渐变 + 每页色块）是**写死的三套**，用户不能换
（`direction.md` §6 把背景算作风格气质的一部分）。这次顺手做了一步整理，为「可选背景」铺路：

- 纸面背景收敛成 `.scatter-prototype` 上的三个 CSS 变量：`--paper-color / --paper-image / --paper-size`，
  三种风格只是这三组值；预览的整条带子与导出画布的单页**共用同一组变量**（之前导出那边重复写了一遍颜色）。
- 因此之后做可选背景，就是换这几组变量（或按用户选择挂不同 class），不需要同时改预览、导出、以及
  逐页切背景的逻辑 —— 切页逻辑只依赖 `background-position-x` 的位移，与背景内容无关。
- 材质层（Weekend 撕纸 / 胶带，`next-development.md` 阶段 C）仍然挂在卡片之上，不参与分页。

## 11. 三种风格的差异诊断与修复

**起因：** 产品反馈「muse 和 weekend 好像差别没那么大」。

**诊断（同一组照片、同一 seed、10 张 × 6 种子）：**

| 指标 | gallery | muse | weekend | 说明 |
| --- | --- | --- | --- | --- |
| 平均 / 最大旋转 | 0° / 0° | 0.22° / 0.45° | 0.85° / 1.79° | 只有旋转真在起作用，幅度又太小 |
| 同页最大/最小面积比 | 1.76 | 1.75 | 1.75 | **尺寸完全没有风格差异** |
| 实际轻叠处数 | 0 | 0 | 0 | **一次都没发生** |
| 像素差异（含背景） | — | gallery 17.06 | gallery 21.29 | muse-weekend 14.81，差的主要是背景色 |

**两个根因（都是实现问题，不是设计问题）：**

1. **风格的尺寸参数是死代码。** `sizeFor()` 写的是 `recipe?.anchorShort ?? style.anchorShort`，
   而 smart 模式每页都有 recipe（2/3/4 张各一套），所以 `style.anchorShort`（.47/.43/.41）与
   `fragmentRange`（.1/.14/.18）**永远不会被读到**。证据：三风格的尺寸差只有 0.03%（1080 上是 0.3px），
   同页面积比一模一样。
2. **轻叠分支形同虚设。** 它写在「并排留缝」之后，只有并排无解时才轮到；而且相叠量按卡片宽度的百分比
   （最多 5.9%）算，远大于 2–5px 白边提供的缓冲，于是任何相叠候选都会被「内容区不得碰撞」判据拒掉。

**修复：**

- 风格系数真正参与：`smartRecipeFor(count, style)` 用 `anchorScale / fragmentScale / fragmentRangeScale`
  调整基准 recipe（而不是被 recipe 遮蔽）。
- 轻叠改成「白边预算」：相叠量 = 两张白边总宽 × `overlapUse`（白边本来就是碰撞缓冲，所以内容区永远不接触），
  并把相叠提为**优先贴法**（不然它永远轮不到）。
- 旋转分档拉开：gallery 0、muse ±0.2°、weekend ±2.6°。
- **旋转安全**：碰撞判据从「内容区」改成「内容区 + 旋转外扩」的安全盒，并排间隙也按旋转让位 ——
  旋转放大后内容区仍然不碰撞（有测试用旋转后的矩形独立复算）。

**修复后（10 张 × 20 种子）：**

| 指标 | gallery | muse | weekend |
| --- | --- | --- | --- |
| 平均 / 最大旋转 | 0° / 0° | 0.1° / 0.2° | 1.24° / 2.59° |
| 同页最大/最小面积比 | 1.67 | 1.75 | 2.27 |
| 有卡片相叠的页 | 0 / 100 | 8 / 100 | 1 / 100 |
| 触发整页缩放的页 | 2 / 100 | 2 / 100 | 1 / 100 |
| 内容区碰撞 | 0 | 0 | 0 |

**一个物理约束（记录以免误判为 bug）：** 旋转与轻叠互斥 —— 2.6° 旋转扫出的宽度（约 12px@1080）
已经超过两张白边的总缓冲（4–10px），所以 weekend 的相叠页反而少（1/100），
轻叠主要由 muse 承担。要让 weekend 也能明显相叠，得先把白边加厚（那就是「拍立得白边」的材质层）。

**测试固化：** 新增 4 条「三种风格必须真的可以分辨」测试（旋转分档、尺度对比分档、轻叠差异、
以及风格差异不得牺牲硬边界）。这组测试的意义是：以后任何风格参数改动如果又变成死代码，测试会失败。

**仍然相近的一对：** muse 与 weekend 的像素差异（18.15）仍小于 gallery 与它们的差异（33.04 / 29.80），
因为两者的背景都是暖灰纸面。这部分差异按 `direction.md` §6 应该由「背景 + 细线 / 文字」承担 ——
也就是下一步的背景库与材质层，而不是继续在几何上做文章。
