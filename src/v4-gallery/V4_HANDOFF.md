# V4 Gallery — 交接文档

## 先读这段

这是 **V4 Gallery 原型**，入口是：

```text
/?prototype=v4-gallery&seed=gallery-01
```

当前目标不是电子书、自由拼图或 Canva 模板。用户上传 6–10 张照片后，应得到一张 4:5 的 Overview：它像参考图中的一块紧凑、不规则、逐格长出的照片群。照片群内部有主次，但不能是“大主图四周挂小图”。

用户已明确否定当前线上版本的视觉结果。请把当前布局当作可运行的技术底座，**不要把它当作视觉方向**。

## 严格边界

- 只改 `src/v4-gallery/`。
- **不要修改** `src/v1-book/`、`src/v2-collage/`、`src/v3-carousel/` 或 `src/shared/`。
- V3 正由另一位 Agent 开发；不要重构、格式化、移动或顺手修复其他版本。
- 工作区可能有其他人的未提交改动。提交时只能暂存明确修改的 V4 文件。
- 不要把用户测试照片加入仓库。可本地使用：`D:\S9 to phone\2026-9-6-南昌路`。

## 视觉目标：参考图真正要表达什么

参考图不是“所有照片一样大”，也不是瀑布流、等高行或等宽列。它有一个 **紧凑的照片接触关系**：

- 所有照片保留原始横竖比例；可以缩放，不能压扁，优先不裁切。
- 图与图之间只有很窄且一致的缝隙，形成一个连续的、略不规则的整体轮廓。
- 竖图可以跨越上下两个小区域，成为支柱；横图可以横向连接两个区域；小图补在支柱两侧。
- 主图只是群组内较大的一块，通常靠下或靠侧，不能占据整个画布中心。
- 照片群外才有安静留白。不要把留白变成照片群内部的大洞。
- 一组横竖混传应更像“编辑过的接触表 / 拼贴块”，不是一排排图片条带。
- Gallery 风格干净克制：直角、微弱阴影、浅中性背景。不要做大号杂志标题、胶带、撕纸或 Canva 式模板。

图片应能做到自适应。关键不是替每张图固定框，而是：**先选择照片之间谁与谁相接的拓扑，再在该拓扑里用真实比例求出每张图的尺寸和位置。**

## 当前版本为什么不够好

最近提交：`f16a93d`（已发布）。当前 `weaveFrames()` 尝试了“竖图跨两层”的方向，但仍存在根本问题：

1. 它按上传索引硬编码了图片角色和顺序；不是由图片比例/候选构图决定。
2. 它只有一套静态交错骨架，无法自然适配不同的混合比例组合。
3. 之前的版本还尝试过“主图 + 周边图”和“等高照片带”；这两种方向都已被用户否定。不要回退。
4. 当前视觉比条带更接近参考，但仍像一套可辨认的固定模板，而不是参考图那种自然、不规则的紧密照片块。

## 建议替换方案：候选拓扑 + 比例求解

请重写 `buildGalleryOverview()` 的布局策略，不要继续给 `weaveFrames()` 增加补丁。推荐步骤：

1. 为照片计算 `aspect = width / height`，分类为宽图、横图、近方图、竖图、长竖图。
2. 根据照片集合生成 2–4 套**接触拓扑候选**，例如：
   - 一个竖图支柱跨两层，左右由横图桥接；
   - 两个竖图支柱，中间穿插横图；
   - 全竖图时用 3–4 个交错窄列；
   - 全横图时用高低错开的横向带，但不要等高整行。
3. 对每套候选，使用真实比例计算 frame 尺寸。相邻关系应尽量共享边，而不是把每行强制填满。
4. 计算候选得分并选最好的一套：
   - 无碰撞；
   - 照片群内部空洞最少；
   - 群组的宽高比例、密度和主图面积在合理范围；
   - 主图显著大于细节图，但不超过群组面积约一半；
   - 整组居中且保留外部留白。
5. `seed` 只用于同一候选内的小幅位置选择，或同分候选的选择。相同 seed 必须稳定；换 seed 可以改变，但不能变成另一种散乱风格。

优先让“接触关系”正确，再微调视觉尺寸。不要为了填满矩形而裁切图片；不规则外轮廓是允许的，内部大洞不允许。

## 非常重要：4:5 坐标换算

`overviewLayout.js` 中：

```js
export const BOARD_WIDTH = 100
export const BOARD_HEIGHT = 125
const FRAME_ASPECT = BOARD_WIDTH / BOARD_HEIGHT // 0.8
```

布局算法内部建议以“相对于画布宽度的物理单位”计算 `x`、`y`、`width`、`height`。但 CSS 中：

- `left` 和 `width` 的百分比相对于画布宽度；
- `top` 和 `height` 的百分比相对于画布高度。

因此，物理纵向坐标写回 CSS layout units 时要乘 `FRAME_ASPECT`：

```js
tile.y = physicalY * FRAME_ASPECT
tile.height = physicalHeight * FRAME_ASPECT
```

真实渲染比例的断言是：

```js
tile.width / (tile.height / FRAME_ASPECT) === photo.aspect
```

此前把纵向值除以 `FRAME_ASPECT`，会让视觉上的纵向间距被放大 1.25 倍，造成“代码里贴着、页面上有大洞”的假象。不要改回去。

`V4GalleryPrototype.jsx` 已使用 CSS `aspectRatio: aspectOf(tile.photo)` 以及图片 `width: 100%; height: auto`，这是正确的：图片本身不会被 `object-fit: contain` 塞进错误的框。

## 当前交互与图片质量（先保留）

- 点击照片目前是 **原位聚焦**：移动/缩放整张 Overview 画布，而不是把图提到新页面。
- 聚焦原图使用上传文件的 blob URL；Overview 使用较大的预览图。逻辑位于 `lib/photoSources.js`。
- `focusCameraFor()` 的垂直平移使用 `translateY: 50 - scale * centerY`；不要恢复为使用 `BOARD_HEIGHT / 2` 的旧写法。
- 用户曾要求“被上层照片遮住时，上层变玻璃纸透明”，但随后要求先解决比例与构图。目前尚未实现透明遮挡；先把 Overview 构图做到位。

## 验收与检查

至少检查三种输入：全竖图、全横图、横竖混传；以及真实混合照片。每次修改后运行：

```powershell
npm test
npm run build
```

再用浏览器实际看 `?prototype=v4-gallery&seed=gallery-01`，不要只看测试数据或布局对象。视觉验收优先级：

1. 一眼像连续、不规则、紧凑的照片拼贴块；
2. 横竖图真实比例正确，无上下黑边/白边和变形；
3. 主次存在，但没有“一大九小”的挂件感；
4. 同 seed 稳定，重新生成只做受控变化；
5. V1/V2/V3 完全未改。

部署仍是现有 GitHub Pages 工作流：只提交 V4 文件，推送 `main` 后等待 `deploy.yml` 成功。
